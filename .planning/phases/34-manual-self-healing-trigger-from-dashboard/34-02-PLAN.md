<objective>
Generalize the heal pipeline from `POST_CARD`-only to all currently-stale DOM-healable targets (HEAL-03 / D-03, D-04, D-05), and pin the `TRIGGER_HEAL` request/response message contract — including a dedicated busy sentinel — in ONE shared module so the content-side listener (Plan 03) and the dashboard sender (Plan 04) agree without divergence.

`triggerHeal` is hardcoded today: `deriveHeuristicCandidates('POST_CARD', container)`, `insertCandidate('POST_CARD', …)`, `rederiver.rederive('POST_CARD', skeleton)`. Generalize it to iterate an internal stale-target list — where staleness is computed LIVE against the container via `resolve(target)` — route each target by shape, and return a per-target outcome, while preserving the validate-before-write gate (HEAL-05 / D-07) untouched.

The only pre-existing staleness signal (`selectorSessionMisses`, written by `recordMiss`) is DEAD — `recordMiss()` has zero runtime call sites in `src/`, so the set is always empty. Healing off it would heal nothing and fail HEAL-03/HEAL-04. We therefore compute staleness live inside `triggerHeal`, which already holds the live container: a target is stale when its current active selector (`resolve(target)`) fails to match the live container. This reuses the existing `resolve()` machinery (D-03's "reuse existing staleness signals" intent) rather than inventing a new persisted metric.

Purpose: This is the core enabling change. The content listener and dashboard UI both depend on the generalized signature, the pinned envelope, and the busy sentinel.
Output: New `src/shared/heal-messages.ts` (contract + busy sentinel); generalized `heal.ts` returning `HealOutcome[]`.
</objective>
