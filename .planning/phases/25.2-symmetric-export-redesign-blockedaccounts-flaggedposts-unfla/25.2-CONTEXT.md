# Phase 25.2: Symmetric export redesign (blockedAccounts + flaggedPosts + unflaggedPosts) - Context

**Gathered:** 2026-06-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Restructure the dashboard **Export JSON** (`buildJsonExport` in `src/dashboard/dataManagement.ts`) so the Phase 26 eval gets a richer, post-centric dataset. The export gains a NEW top-level post-centric `flaggedPosts[]` array (positives, sourced from the existing `storedPosts`), sitting symmetrically alongside the existing top-level `unflaggedPosts[]` (negatives, shipped in 25.1). The `flaggedAccounts[]` array is retained but each account's `status` enum is replaced with a `blocked: boolean`.

**This is an export-shape-only change.** No content-script or capture work — it reshapes data already in `chrome.storage.local` at export time.

**In scope:** `buildJsonExport` output shape; the dashboard storage read that feeds it; the `dataManagement.test.ts` updates; a `FlaggedPost` type if the planner wants one; amending `26-CONTEXT.md` to match the new contract.
**Out of scope:** capturing text for the 35–60 "flagged-but-not-hidden" band (the positives gap — see Deferred); the eval runner itself (Phase 26); CSV export changes; any labeling UI (labels are hand-added to the exported JSON).

> **Naming note:** The ROADMAP title says "blockedAccounts". During discussion the user revised this — the account array stays named `flaggedAccounts` (all flagged accounts, not filtered to blocked-only) with a `blocked: boolean` per entry. See D-04/D-05. The roadmap title is now slightly stale; the decisions below are authoritative.
</domain>

<decisions>
## Implementation Decisions

### Overall structure (Area: Replace vs additive)
- **D-01:** Final top-level export shape is `{ exportedAt, flaggedAccounts[], flaggedPosts[], unflaggedPosts[] }`. `flaggedPosts[]` is NEW; `unflaggedPosts[]` is unchanged from 25.1; `flaggedAccounts[]` is retained (see D-04/D-05).
  - **Decision evolution:** The discussion initially locked "full replace — remove `flaggedAccounts`, rename to a filtered `blockedAccounts`." The user then revised in the blockedAccounts area (D-04/D-05): keep `flaggedAccounts`, don't filter, add a `blocked` flag instead. **D-04/D-05 supersede the earlier full-replace/rename framing.** The genuinely new thing is the top-level `flaggedPosts[]`.

### flaggedPosts (NEW — Area: flaggedPosts source + shape)
- **D-02:** Source is the **existing `storedPosts`** store (hidden posts, score ≥ `autoHideThreshold`/default 60) reshaped into a flat top-level array. Export-only; no new capture. **Accepted consequence:** the 35–60 "flagged-but-not-hidden" band has no stored text, so `flaggedPosts` is effectively "hidden posts" with a hole in that band (see Deferred). Confirmed acceptable for this phase.
- **D-03:** Entry shape **mirrors `unflaggedPosts`** for symmetry: `{ urn, authorId, authorName, text, score, hiddenAt, label? }`.
  - Keep the **native `hiddenAt`** as the timestamp (vs `unflaggedPosts`'s `seenAt`) so the field stays truthful — these posts were hidden, not merely seen.
  - **Omit `engineUsed`** — it was never recorded at hide time for `storedPosts` (only `unflaggedPosts` carries it).
  - Include an **optional user-added `label`** (`"ai" | "human"`) for eval use. Stored **UNLABELED** by default — the extension NEVER writes `label`, identical to 25.1 D-06. The export only emits `label` when present (mirror the `unflaggedPosts` conditional spread in `buildJsonExport`).

### flaggedAccounts (Area: blockedAccounts content)
- **D-04:** Keep the array named **`flaggedAccounts`**, containing **all** flagged accounts (pending + blocked + dismissed). Do NOT filter to blocked-only and do NOT rename to `blockedAccounts`. (User override of the roadmap framing.)
- **D-05:** **Replace the `status` enum with a `blocked: boolean`** on each exported account (`blocked = (status === 'blocked')`). The `status` field is dropped from the export output. This is an **export-shape transform only** — `FlaggedAccount.status` in storage/types is unchanged; the boolean is derived in `buildJsonExport`.
  - **Known tradeoff (flagged to user, accepted):** collapsing `status` into a boolean loses the `pending` vs `dismissed` distinction in the export (both become `blocked: false`). Acceptable for the eval's purposes.
- **D-06:** **Keep the nested `posts[]`** inside each `flaggedAccounts` entry (current `{ urn, score, text, hiddenAt }` shape). The same hidden-post data therefore appears in two places (nested under accounts AND in top-level `flaggedPosts[]`) — this duplication is **intentional**: the user wants the account→posts view preserved alongside the new post-centric array.

### Cross-phase contract (Phase 26 eval)
- **D-07:** Because positives now live in top-level **`flaggedPosts[]`** (not only `flaggedAccounts[].posts[]`), **amend `26-CONTEXT.md` as part of this phase.** The eval walker should read the two top-level post-centric arrays: **`flaggedPosts[]`** (positives) + **`unflaggedPosts[]`** (negatives). The nested `flaggedAccounts[].posts[]` becomes redundant for the eval (harmless duplicate). Update the existing 25.1 amendment block in `26-CONTEXT.md` D-07/D-08 to reflect `flaggedPosts[]` as the positive source; positive class for metrics = `ai`; unlabeled entries skipped (per 26 D-09); stored `score` ignored (eval re-scores fresh).

### Claude's Discretion
- Whether to introduce a named `FlaggedPost` TypeScript interface (in `src/shared/types.ts`) or inline the mapped shape in `buildJsonExport` — planner's call. If named, mirror the `UnflaggedPost` doc-comment style.
- Exact `dataManagement.test.ts` assertions for the new shape (presence of `flaggedPosts[]`, `blocked` boolean, absence of `status`, label conditional, empty-array defaults).
- `buildJsonExport` signature: `flaggedPosts` derives from the existing `posts: StoredPost[]` parameter (same source as the nested posts) — no new parameter likely needed; planner confirms.
</decisions>

## Existing Code Insights

### Reusable Assets
- `buildJsonExport` `unflaggedPosts` mapping (dataManagement.ts L37–45): exact template for the new `flaggedPosts` mapping, including the `...(p.label !== undefined ? { label: p.label } : {})` conditional-label idiom.
- `UnflaggedPost` interface (types.ts L196+): the doc-comment + field template if a `FlaggedPost` type is introduced.
- `StoredPost` (types.ts L173–186): the source records for `flaggedPosts` (already passed into `buildJsonExport` as the `posts` param, currently used only to build nested account posts).

### Established Patterns
- Score bands: `< FLAG_THRESHOLD` (35) → unflagged/`unflaggedPosts`; `FLAG_THRESHOLD..autoHideThreshold` → flagged-not-hidden (counted only, **no text stored** — the gap); `>= autoHideThreshold` (60 default) → hidden + stored in `storedPosts` → `flaggedPosts`.
- chrome.storage.local only; export is a pure transform over already-stored data; no service-worker / content-script involvement.
- UNLABELED-by-default discipline (25.1 D-06): the extension never writes `label`; only the user does, post-export.

### Integration Points
- `buildJsonExport` is the sole transform point — both the `blocked` derivation and `flaggedPosts[]` construction happen there.
- Dashboard `index.tsx` already reads all needed keys (`flaggedAccounts`, `storedPosts`, `unflaggedPosts`); verify the call passes `storedPosts` through.
- Phase 26 eval walker — the downstream consumer (D-07).

<specifics>
## Specific Ideas

- The user inspected a live export (`linkedin-blocker-2026-06-14 (4).json`): 79 flagged accounts (mostly `status: "pending"`, `posts: []` because they scored < hide threshold), 8 `unflaggedPosts`. This concretely confirms the 35–60 text gap (D-02) and motivated the `status`→`blocked` simplification (D-05).
- The user explicitly wants the account→posts nested view kept (D-06) even though it duplicates `flaggedPosts[]` — readability over deduplication.
</specifics>
