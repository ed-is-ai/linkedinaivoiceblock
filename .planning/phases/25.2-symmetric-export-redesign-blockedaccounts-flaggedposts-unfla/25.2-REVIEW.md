# Phase 25.2: Code Review Report

**Reviewed:** 2026-06-14T20:35:24Z
**Depth:** standard
**Files Reviewed:** 3
**Status:** issues_found

## Summary

The phase reshapes `buildJsonExport` into a three-array symmetric export: top-level
`flaggedAccounts[]` (now with a `status`->`blocked` boolean transform and `status`
stripped), a new top-level `flaggedPosts[]`, and the existing `unflaggedPosts[]`, while
retaining the nested per-account `posts[]`. A new export-only `FlaggedPost` interface is
added to `types.ts`.

No security issues and no correctness BLOCKERs were found. The mapping logic is sound: the
ISO conversions reference the still-in-scope `a`/`p` objects correctly, the `blocked`
transform matches `status === 'blocked'`, and `status` is removed via destructuring before
spreading. The test suite covers the new shapes well.

However, the `flaggedPosts[].label` plumbing is **dead in production** — `StoredPost` has no
`label` field and nothing in the codebase ever writes one to `storedPosts`, so the
conditional label-forwarding can only ever fire in tests that inject the field manually. This,
plus a `...rest` spread that silently re-emits internal fields and a redundant data
duplication across the three arrays, are the main concerns. None block shipping.

## Warnings

### WR-01: `flaggedPosts[].label` forwarding is unreachable in production data

**File:** `src/dashboard/dataManagement.ts:41-52`
**Issue:** `flaggedPosts` is built from `posts: StoredPost[]`. `StoredPost` (types.ts:173-186)
has **no `label` field**, and `persistStoredPost` never writes one (unlike `UnflaggedPost`,
whose `label` is documented as user-added-after-export). To forward a label the code casts
`p as StoredPost & { label?: string }` and conditionally spreads `labelEntry`. In real exported
data this branch is never taken — `typed.label` is always `undefined`. The only thing that
exercises it is the test at dataManagement.test.ts:199-203, which manually constructs
`{ ...makePost(), label: 'ai' }`. The `FlaggedPost.label` doc (types.ts:242-246) says the label
is "added by the user after editing the exported JSON" — i.e. it is added *to the output file*,
not present on the *input* `StoredPost`. So sourcing `label` from the input is conceptually
inconsistent with the documented data flow. This is defensive code propped up by a test that
does not reflect any real storage state.
**Fix:** Either drop the label-forwarding entirely from `flaggedPosts` (matching the documented
"user edits the exported JSON" flow, and remove the test that injects it), or — if forwarding is
intended for symmetry — add `label?: string` to `StoredPost` and actually populate it somewhere
so the path is reachable. Recommended:
```typescript
flaggedPosts: posts.map((p): FlaggedPostExport => ({
  urn: p.urn,
  authorId: p.authorId,
  authorName: p.authorName,
  text: p.text,
  score: p.score,
  hiddenAt: new Date(p.hiddenAt).toISOString(),
})),
```

### WR-02: `...rest` spread on accounts silently re-emits all unlisted internal fields

**File:** `src/dashboard/dataManagement.ts:26-40`
**Issue:** `flaggedAccounts` uses `const { status, ...rest } = a; return { ...rest, blocked, ... }`.
This deliberately strips only `status`, but spreads everything else on `FlaggedAccount` into the
export, including `hiddenPostUrns` (types.ts:105). That array now duplicates information already
carried by the nested `posts[]` and the new top-level `flaggedPosts[]`, and any future field added
to `FlaggedAccount` is auto-leaked into the exported JSON with no test catching it. For an export
contract that the phase is explicitly trying to make symmetric and well-defined, an opt-out spread
is fragile — the export shape should be an explicit allow-list.
**Fix:** Replace the spread with an explicit projection of the intended export fields, e.g.:
```typescript
flaggedAccounts: accounts.map(a => ({
  authorId: a.authorId,
  authorName: a.authorName,
  authorProfileUrl: a.authorProfileUrl,
  compositeScore: a.compositeScore,
  postCount: a.postCount,
  peakScore: a.peakScore,
  signals: a.signals,
  blocked: a.status === 'blocked',
  firstSeenAt: new Date(a.firstSeenAt).toISOString(),
  lastSeenAt: new Date(a.lastSeenAt).toISOString(),
  posts: (postsByAuthor[a.authorId] ?? []).map(/* ... */),
}))
```
At minimum, add a test asserting the exact key set of `flaggedAccounts[0]` so accidental field
leakage is caught.

### WR-03: `as` type assertion masks the missing `label` field on `StoredPost`

**File:** `src/dashboard/dataManagement.ts:42`
**Issue:** `const typed = p as StoredPost & { label?: string };` is a type assertion that widens
`p` to a shape it does not actually have. This defeats the type checker: if `StoredPost` legitimately
gained a `label` field later, or if the field were renamed, the assertion would hide the mismatch.
Assertions that invent fields are exactly the kind the standard-depth TS checks call out. It is only
needed because of the unreachable forwarding in WR-01.
**Fix:** Remove the assertion. If WR-01 is resolved by dropping label-forwarding, this line goes away
entirely. If label-forwarding is kept, add the field to `StoredPost` so the access is type-safe without
a cast.

## Info

### IN-01: `flaggedPosts[]` and nested `posts[]` are redundant projections of the same source

**File:** `src/dashboard/dataManagement.ts:33-53`
**Issue:** Both the per-account nested `posts[]` and the top-level `flaggedPosts[]` are derived from
the same `posts: StoredPost[]` input — every stored post is emitted twice (once flat, once nested
under its matching account, if any). This roughly doubles the JSON payload for posts and creates two
sources of truth for the same records. It is the documented intent of the "retain nested posts[]"
requirement, so this is informational, but worth confirming downstream consumers actually need both
rather than one.
**Fix:** If only the flat `flaggedPosts[]` is consumed for eval, consider whether the nested
`posts[]` can be reduced to URN references. No change required if both shapes are intentional.

### IN-02: Inline export-projection type instead of a named alias

**File:** `src/dashboard/dataManagement.ts:41`
**Issue:** The `flaggedPosts` mapper is annotated with an inline
`Omit<FlaggedPost, 'hiddenAt'> & { hiddenAt: string }`. The same string-timestamp transform is applied
to accounts (`firstSeenAt`/`lastSeenAt`) and `unflaggedPosts` (`seenAt`) without any annotation, so the
codebase is inconsistent about whether the serialized shape is named. A named alias (e.g.
`type FlaggedPostExport = Omit<FlaggedPost, 'hiddenAt'> & { hiddenAt: string }`) would document the
export contract once and be reusable.
**Fix:** Extract the serialized shape into a named type and reuse it; optionally do the same for the
account and unflagged projections.

### IN-03: `FlaggedPost` is declared but never referenced as a value type at runtime

**File:** `src/shared/types.ts:229-247`
**Issue:** `FlaggedPost` is imported into dataManagement.ts but used only inside the inline
`Omit<...>` annotation (line 41); no variable, parameter, or return is typed as a plain `FlaggedPost`.
The interface's `hiddenAt: number` never matches any produced value (the export always stringifies it),
so the interface as written models a shape that is never actually constructed. This is acceptable as a
"source-of-truth field list" but is mildly misleading.
**Fix:** Document in the `FlaggedPost` JSDoc that the exported form replaces `hiddenAt: number` with an
ISO string, or define the export variant alongside it (see IN-02) so the relationship is explicit.
