## 1. System Classification

**System Type:** Extraction (single-shot structured extraction — input: PII-stripped DOM skeleton; output: a CSS selector string)

**Description:**
A repair mechanism inside a Chrome MV3 extension. When the content script detects that LinkedIn's DOM has changed and the active post-card selector matches zero posts on a genuinely-active feed, it asks the system to re-derive a working selector. Local structural heuristics run first (no API call). Only if heuristics produce no candidate that passes the validation gate, and the user has configured an Anthropic API key, does a Claude fallback run **in the service worker** (CORS blocks content-script fetches to api.anthropic.com). The LLM receives only a sanitized structural DOM skeleton — all text, `href`, `src`, and `aria-label` values stripped — and returns ranked candidate CSS selector strings. "Good" = a returned/heuristic selector that, when run against the live feed, matches 2–50 post cards, finds author links in >50% of them, and finds post-body text — i.e., it actually restores post detection without contaminating with ads or sidebar elements, and without leaking PII or executing model output as code.

**Critical Failure Modes:**
1. **PII leakage** — post text, author names, headlines, profile/image URLs, or `aria-label` content reaches the Anthropic API. The sanitizer must strip every text node, `href`, `src`, and `aria-label` before the skeleton leaves the browser.
2. **Selector-string code execution / prompt injection** — a model-proposed (or page-influenced) string is passed to `eval`/`Function`/`innerHTML` instead of being used only as a plain argument to `querySelectorAll`. Page content must never be able to escalate into code execution.
3. **Writing a bad candidate to storage** — a selector that matches `body`/`html`/`*`, matches outside the 2–50 range, or matches ads/sidebar instead of post cards gets persisted, silently breaking detection worse than the original breakage. The validation gate must block every write.
4. **False-positive healing** — breakage detection fires on a logged-out page, skeleton-loader, non-feed URL, or genuinely empty feed, triggering needless re-derivation (and possibly an API call). The Core-4 guards plus 30s debounce must prevent this.
5. **Runaway API cost** — the LLM fallback is called repeatedly (per post, in a loop, or on every breakage flap), bypassing the single-flight latch, the ≥5-minute cool-off (persisted across service-worker restarts), or the per-day hard cap.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Developer tooling / browser extension (resilient DOM scraping against a hostile, frequently-changing third-party SPA — LinkedIn)

**User Population:** Two distinct groups. (1) Non-technical end users of the LinkedIn Blocker extension whose feed silently stops being filtered when LinkedIn redeploys its front end — they experience the failure as the extension appearing to work while showing no filtering effect. (2) The extension maintainer who otherwise must hand-patch selectors after every LinkedIn front-end deploy and push a new extension release.

**Stakes Level:** Medium — with one genuinely High sub-risk

The overall stakes are medium: a wrong selector degrades a free consumer productivity tool, not a clinical or financial system. The one High sub-risk is PII exfiltration: if post text, author names, or profile URLs reach the Anthropic API, the user has had personal data sent to a third party without informed consent, which has genuine privacy harm and potential regulatory exposure (GDPR for EU users). API cost waste is a real but lower-stakes concern — a runaway heal loop can burn the user's own Anthropic credits.

**Output Consequence:** The re-derived CSS selector string is persisted to `chrome.storage.local` via `SelectorRegistry` and immediately used by the content script to find post cards on the live LinkedIn feed. A bad candidate that passes the validation gate has three downstream effects: (a) posts stop being detected and hidden, silently breaking the extension's core function; (b) if the selector matches ads or sidebar nodes, ad elements may be hidden, causing an unexpected and confusing visual layout; (c) a stored bad selector persists across browser restarts until a manual reset or a future heal cycle corrects it.

### What Domain Experts Evaluate Against

A front-end engineer or extension maintainer looking at a candidate selector in DevTools judges it on five dimensions:

---

**Dimension: Selector durability against LinkedIn redeploys**
Good (expert accepts): Selector uses only `data-*` attributes, `role`, semantic HTML elements (`article`, `main`), or structural combinators anchored to stable accessibility landmarks — e.g., `div[data-urn*='activity']` or `[role='article'][data-id]`. Two engineers independently opening the same selector in DevTools's Elements panel and running `document.querySelectorAll()` would both confirm it targets post cards.
Bad (expert flags): Selector contains a hashed or utility CSS class name (e.g., `.feed-shared-update-v2`, `.artdeco-card`). LinkedIn rebuilds class names on every webpack deploy; such a selector will break again within days. This directly violates CLAUDE.md constraint #1.
Stakes: Critical
Source: CLAUDE.md constraint #1; production scraping practitioners — hashed class names are documented as the primary cause of selector rot in SPA scraping (Medium/Geek Culture, 2021; rebrowser.net CSS selector guide, 2025)

---

**Dimension: Match count sanity — not too few, not too many**
Good (expert accepts): Running the candidate selector against `document.querySelectorAll()` on an active LinkedIn feed returns between 2 and 50 elements. This range confirms the selector targets individual post cards (not the whole feed container, not a single element, not sidebar/ad nodes that vastly outnumber posts).
Bad (expert flags): Match count of 0 (selector missed everything — still broken), 1 (too specific, will miss most posts), or >50 (too broad — catching sidebar widgets, skeleton loaders, or ad slots alongside real posts). Match count equal to the total element count is an instant red flag indicating `*` or `body` was returned.
Stakes: Critical
Source: 23-CONTEXT.md validation gate — the 2–50 range is a locked project decision; ADAPT-07 and ADAPT-08 in REQUIREMENTS.md

---

**Dimension: Post-card structural integrity — author link and body text present**
Good (expert accepts): At least 50% of matched elements contain a child anchor element pointing to a `/in/` profile URL (author link), and at least one matched element contains non-empty text in a child element (post body). This confirms the selector is finding real post cards, not UI chrome.
Bad (expert flags): Matched elements contain no anchor links, no profile URLs, or no readable text content. This indicates the selector has latched onto skeleton-loader placeholders, collapsed ad units, or LinkedIn's floating action bar — all of which produce a match count in the valid range but contain no post content.
Stakes: High
Source: 23-CONTEXT.md validation gate (author-link ratio >50%, post-text presence check); practitioner knowledge of LinkedIn's skeleton-loader DOM

---

**Dimension: Ad and sponsored content isolation**
Good (expert accepts): None of the matched elements carry LinkedIn's sponsored-content markers (e.g., `data-sponsored`, presence of a 'Promoted' label node, or known ad container roles). The selector finds organic posts only.
Bad (expert flags): Matched elements include sponsored posts or ad units. This means the extension hides paid promotions alongside organic AI-generated posts — potentially causing unexpected layout breaks and creating ToS ambiguity about what the extension is hiding.
Stakes: Medium
Source: ADAPT-03 validation gate (sponsored-contamination rejection); LinkedIn ToS on automated interaction with ad placements

---

**Dimension: PII boundary — nothing user-identifiable leaves the browser**
Good (expert accepts): The DOM skeleton sent to the Anthropic API contains only tag names, `data-*` attribute names and values, `role` attributes, and nesting structure. All text nodes, `href` values, `src` values, and `aria-label` values are absent. A reviewer diffing the sent skeleton against the live DOM cannot reconstruct any author name, post text, or profile URL.
Bad (expert flags): Any text node content, `href` containing `/in/` profile paths, `src` containing CDN image URLs, or `aria-label` values containing names or post snippets appear in the payload. Even a single field leaking a real name or profile URL constitutes a PII breach — the sanitizer has failed.
Stakes: High (Critical for EU/GDPR users)
Source: ADAPT-04 and ADAPT-10 in REQUIREMENTS.md; GDPR Article 4 (personal data definition covers name, profile photo URL, and post content); LinkedIn ToS Section 8.2 (no scraping user data)

### Known Failure Modes in This Domain

1. **Selector rot on LinkedIn redeploys** — LinkedIn's front-end build pipeline hashes CSS class names on every deploy (confirmed production pattern across SPAs using webpack/css-modules). A selector that worked Monday breaks Tuesday when LinkedIn ships a new build. This is the primary trigger for the self-healing system and the domain's baseline failure mode.

2. **Skeleton-loader false match** — LinkedIn renders placeholder skeleton cards (grey animated boxes with no content) while the real feed loads. These DOM elements often share structural patterns with real post cards (similar nesting depth, similar `data-*` attribute presence) but contain no text and no author links. A heal cycle that fires too early — before the real feed is populated — will derive a selector that matches skeletons and passes a match-count check, then silently fails the author-link and post-text checks. The Core-4 guards (30s debounce, session activity check, feed container present) are the primary defence.

3. **Heal-to-wrong-element** — The heuristic or LLM produces a selector that matches a real LinkedIn element type (e.g., notification cards, job recommendation cards, 'People you may know' widgets) that lives in the feed DOM alongside post cards. These elements pass match-count validation (5–15 matches) and may even contain author-like anchor links, but they are not post cards. Without the post-body text check they would be written to storage, silently breaking detection for the current session and all subsequent ones until a manual reset.

4. **A/B DOM variant divergence** — LinkedIn regularly runs A/B tests that serve structurally different DOM to different user cohorts. A selector derived from the DOM served to the maintainer's account may not match the DOM served to an end user's account (different `data-*` attribute names, different nesting). The heal cycle fires for the end user, derives a working selector for their variant, and writes it to their local storage — this is correct behaviour, but the reference dataset for eval must include both DOM variants to avoid false confidence from testing only one.

### Regulatory / Compliance Context

**LinkedIn Terms of Service — automated interaction prohibition**
LinkedIn's User Agreement (Section 8.2) prohibits use of "robots, spiders, scrapers, or other automated means to access the Services" and explicitly lists "browser plugins and add-ons" that scrape data. This project's existing design decision to never programmatically click LinkedIn UI (CLAUDE.md constraint #3) exists precisely to stay within a defensible ToS posture. Phase 23 must not add any automated interaction — the heal cycle reads DOM structure only, never clicks, never navigates, never simulates user actions. LinkedIn has actively enforced this ToS in 2025 (Apollo.io page removal, Proxycurl shutdown).

**ADAPT-10 — PRIVACY.md disclosure requirement**
REQUIREMENTS.md ADAPT-10 mandates that if the LLM fallback ships, `PRIVACY.md` must disclose that a sanitized structural description of the feed layout (no text, no PII) may be sent to the Anthropic API. This is not optional — it is a locked requirement. The disclosure covers the data minimisation argument (structural skeleton only) and gives users the choice to not configure an API key, keeping all processing local.

**GDPR (EU users) — personal data in DOM**
LinkedIn post text, author names, and profile URLs are personal data under GDPR Article 4 (they identify or are reasonably linkable to natural persons). If the sanitizer fails to strip these before the DOM skeleton is sent to Anthropic's API, the extension becomes a data processor sending personal data to a third-party sub-processor (Anthropic) without a lawful basis or data processing agreement — a GDPR violation. This is the regulatory dimension of the PII leakage critical failure mode. The sanitizer's strip-before-send design is the primary control; the PRIVACY.md disclosure (ADAPT-10) is a supporting transparency measure.

**No other regulations identified** — this is a consumer browser extension with no financial, clinical, or government-sector scope. HIPAA, FCA, and similar sector-specific regulations do not apply.

## 2. Framework Decision

**Selected Framework:** Direct Anthropic Messages API via `fetch` — **no orchestration framework**

**Version:** Anthropic Messages API `/v1/messages` (`anthropic-version: 2023-06-01`), called from the MV3 service worker. Reuses the exact pattern already shipped in `src/background/index.ts` for `SCORE_POST` (LLMDetector). No new npm dependency is added.

**Rationale:**
Phase 23's LLM step is a single-shot structured extraction: send a PII-stripped DOM skeleton, receive a CSS selector string. It runs inside a Chrome MV3 service worker, where only the native `fetch` API is available — there is no Node.js runtime to host an orchestration framework, and bundling one into the extension would add weight for zero benefit. The project already calls `api.anthropic.com/v1/messages` directly from the service worker (content script sends a message → worker fetches → responds); Phase 23 replicates this verbatim with a new `REDERIVE_SELECTOR` message handler. A direct call keeps full control over the privacy boundary (caller strips the DOM), the rate-limiting logic (single-flight latch + cool-off + daily cap in worker code), and response handling (treat the selector as a plain string, never `eval`). This is the documented anti-pattern to avoid: using a framework for a simple single-call use case adds abstraction, latency, and debugging cost.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangChain / LangGraph (TS) | Require a Node.js server runtime; add bundle weight incompatible with an MV3 service worker; framework overhead is an anti-pattern for a single linear call. LangGraph (TS) is the only fallback *if* a server-side companion is ever added. |
| Claude Agent SDK | Designed for server-side autonomous agents with MCP/filesystem/shell access; introduces a dependency and bundle weight; the raw `fetch` already does everything required. |
| OpenAI Agents SDK | Optimized for OpenAI; project is locked to Anthropic. |
| CrewAI / Haystack / Google ADK | Python-only (or Gemini-locked); cannot run in a TypeScript browser extension. |

**Vendor Lock-In Accepted:** Yes (Anthropic) — already accepted project-wide via the existing LLMDetector. The fallback is optional and only activates when the user supplies their own Anthropic API key; the extension functions (heuristics + seed selectors) with no key configured.

### Entry Point Pattern

This is the minimal, copy-paste-runnable pattern for Phase 23's `rederiveSelector` call in `src/background/index.ts`. It mirrors `scorePost()` exactly in structure.

```typescript
// src/background/index.ts  (add alongside existing scorePost function)

const REDERIVE_SYSTEM_PROMPT = `You are a CSS selector analyst for a Chrome extension that scrapes LinkedIn post cards.
The extension's post-card selector has broken (matches 0 elements on an active feed).
You will receive a PII-stripped structural DOM skeleton of the LinkedIn feed.
All text content, href values, src values, and aria-label values have been removed.
Only tag names, data-* attributes, role attributes, and nesting are present.

Return ONLY a JSON object — no markdown, no commentary, no code fences:
{
  "candidates": [
    { "selector": "<css-selector-string>", "rationale": "<one sentence>" },
    { "selector": "<css-selector-string>", "rationale": "<one sentence>" }
  ]
}

Rules:
- Return 1–3 candidates, ranked by confidence (most confident first).
- Each selector must target individual post-card elements, not the feed container.
- Never return body, html, *, or any selector that would match the entire document.
- Use only data-* attributes, role attributes, and structural/semantic selectors.
- Do not use CSS class names — LinkedIn rebuilds class names on every deploy.
- The caller will validate each candidate with querySelectorAll; a passing candidate
  must match 2–50 elements and find author links in >50% of matched elements.`;

async function rederiveSelector(
  target: string,
  domSkeleton: string,
): Promise<{ candidates: Array<{ selector: string; rationale: string }> }> {
  // 1. Load API key from storage (service worker is stateless — read each time)
  const result = await chrome.storage.local.get(['anthropicApiKey']);
  const apiKey = result.anthropicApiKey as string | undefined;
  if (!apiKey) throw new Error('No API key configured');

  // 2. Build request — use claude-haiku-4-5 for speed/cost on this rare repair call
  const requestBody: AnthropicMessagesRequest = {
    model: 'claude-haiku-4-5',
    max_tokens: 256,                   // candidates list fits well within 256 tokens
    system: [
      {
        type: 'text',
        text: REDERIVE_SYSTEM_PROMPT,
        cache_control: { type: 'ephemeral' }, // cache system prompt for repeated calls within 5 min
      },
    ],
    messages: [
      {
        role: 'user',
        content: `Target: ${target}\n\nDOM skeleton:\n${domSkeleton}`,
      },
    ],
    stop_sequences: ['\n\n\n'], // stop early if model starts free-form prose
  };

  // 3. Call the API
  const response = await fetch('https://api.anthropic.com/v1/messages', {
    method: 'POST',
    headers: {
      'x-api-key': apiKey,
      'anthropic-version': '2023-06-01',
      'content-type': 'application/json',
      'anthropic-dangerous-direct-browser-access': 'true',
      'anthropic-beta': 'prompt-caching-2024-07-31',
    },
    body: JSON.stringify(requestBody),
  });

  // 4. Handle HTTP errors
  if (!response.ok) {
    const body = await response.text();
    throw new Error(`Anthropic API ${response.status}: ${body}`);
  }

  // 5. Parse and validate response shape
  const data = await response.json() as AnthropicMessagesResponse;
  const raw = data.content[0]?.text ?? '';

  // Strip any accidental markdown code fences the model may emit
  const jsonStr = raw.replace(/^```(?:json)?\n?/, '').replace(/\n?```$/, '').trim();

  const parsed = JSON.parse(jsonStr) as {
    candidates?: Array<{ selector?: string; rationale?: string }>;
  };

  if (!Array.isArray(parsed.candidates) || parsed.candidates.length === 0) {
    throw new Error('LLM returned no candidates');
  }

  // 6. Coerce and return — validation gate runs in the caller, not here
  return {
    candidates: parsed.candidates
      .filter(c => typeof c.selector === 'string' && c.selector.trim().length > 0)
      .map(c => ({ selector: c.selector!.trim(), rationale: c.rationale ?? '' })),
  };
}
```

### Common Pitfalls

1. **Forgetting `anthropic-dangerous-direct-browser-access: true`** — The Anthropic API sets a CORS restriction that blocks browser-origin requests. Omitting this header causes the `fetch` to fail with a network error (not an HTTP 4xx) from the service worker. Every request to `api.anthropic.com` from a browser context requires this header. See existing usage in `src/background/index.ts`.

2. **Trusting the model's selector string without validation** — The LLM may return a syntactically valid but semantically wrong selector (e.g., matching 200 elements, or targeting `body`). Never pass the returned string to `querySelectorAll` and act on the count without first running the three-gate validation (2–50 match count, >50% author-link ratio, post-text presence). Also reject any string that is exactly `body`, `html`, `*`, or contains `eval` or `javascript:`.

3. **Calling the LLM from the content script** — `api.anthropic.com` blocks CORS for `https://www.linkedin.com` origins. All `fetch` calls to Anthropic must originate from the service worker (`background/index.ts`), not from `observer.ts` or any content-script module. The `REDERIVE_SELECTOR` message pattern mirrors `SCORE_POST` exactly for this reason.

4. **`max_tokens` too large for an extraction task** — Setting `max_tokens: 1024` or higher on a call that should return 1–3 short JSON candidate objects means a truncated or hallucinated response can consume many more output tokens before hitting the cap, increasing cost and parse error rate. 256 tokens is the correct ceiling for this response shape.

5. **Service-worker state loss between the rate-limit check and the API call** — MV3 service workers terminate after ~30s idle. If the single-flight latch and cool-off timestamp are held only in module-scope variables, they are lost when the worker restarts. Rate-limit state (`lastCallTimestamp`, `callsToday`, `inFlight` flag) must be persisted to `chrome.storage.local` before the `fetch` starts and must be read from storage at the start of the rate-limit check — not from an in-memory cache.

## 4. Implementation Guidance

**Model Configuration:**

Use `claude-haiku-4-5` (model ID: `claude-haiku-4-5-20251001`) for the `rederiveSelector` call. Rationale: this is a rare, on-breakage-only call (not per-post), so latency matters more than raw extraction quality. Haiku 4.5 is the fastest available model and the extraction task (identify a CSS selector from a structural skeleton) does not require Sonnet-tier reasoning. If Haiku 4.5 produces poor selectors in practice (logged via TRACE-02 traces in Phase 24), promote to `claude-sonnet-4-6`.

```
model:        claude-haiku-4-5-20251001
max_tokens:   256        (1–3 JSON candidate objects fit comfortably)
temperature:  (omit)     (default 1.0 is fine; this is extraction not generation)
stop_sequences: ['\n\n\n']
```

Do NOT use `claude-sonnet-4-6` as the default for this call. Sonnet is 3x the per-token cost and adds latency for a task Haiku handles adequately. Reserve Sonnet as a manual escalation path if Haiku's selector quality proves inadequate after observing traces.

**Core Pattern:**

The Phase 23 LLM call follows the same three-layer pattern as the existing `SCORE_POST` / `LLMDetector`:

```
Layer 1 — Content Script (sanitizer.ts + rederiver.ts)
  detectBreakage() → guards pass → buildDomSkeleton() → stripPii() → sendMessage(REDERIVE_SELECTOR)

Layer 2 — Service Worker (background/index.ts)
  onMessage(REDERIVE_SELECTOR) → rateLimitCheck() → rederiveSelector(skeleton) → sendResponse(candidates)

Layer 3 — Content Script (validator.ts + SelectorRegistry)
  for each candidate: validateCandidate(selector) → if pass: SelectorRegistry.updateCandidate(target, selector)
```

The validation gate always runs in the content script against the live DOM — the service worker never calls `querySelectorAll` and never writes to `selectorRegistry` directly.

```typescript
// src/content/detector/rederiver.ts — mirrors LLMDetector structure
export class LLMRederiver {
  async rederive(target: string, domSkeleton: string): Promise<string | null> {
    return new Promise((resolve, reject) => {
      chrome.runtime.sendMessage(
        { type: 'REDERIVE_SELECTOR', target, domSkeleton },
        (response) => {
          if (chrome.runtime.lastError) { reject(chrome.runtime.lastError); return; }
          if (response?.error) { reject(new Error(response.error as string)); return; }
          resolve(response.result as string | null);
        },
      );
    });
  }
}
```

**Tool Use:**

No LLM tool-use (function calling) is configured. Phase 23 uses the simplest possible extraction pattern: one `user` turn with the DOM skeleton, one `assistant` turn with a JSON object. The model returns a plain JSON string; the TypeScript caller parses and validates it. Adding tool definitions would require the model to emit a `tool_use` content block, complicate the response parser, and add no value for a single-shot extraction task.

**State Management:**

All state lives in `chrome.storage.local`. The service worker is stateless between invocations. These keys must be read from storage at the start of every rate-limit check and written back before the `fetch` begins:

```typescript
// Keys written/read by the rate-limit guard in background/index.ts
interface RateLimitState {
  lastRederiveCallMs: number;   // epoch ms of most recent LLM call; cool-off check
  rederiveCallsToday: number;   // count since midnight UTC; hard daily cap
  rederiveDateKey: string;      // 'YYYY-MM-DD' — reset rederiveCallsToday when changed
  rederiveInFlight: boolean;    // single-flight latch; cleared in finally block
}
```

The `rederiveInFlight` latch prevents two concurrent `REDERIVE_SELECTOR` messages from both reaching the API (e.g., two tabs detecting breakage simultaneously). Set it to `true` before the `fetch` call; clear it in a `finally` block.

Do not store the DOM skeleton, the raw LLM response, or the full candidate list in storage. Only the winning candidate (after validation) is written — by the content script via `SelectorRegistry.updateCandidate()`, which already handles the storage write.

**Context Window Strategy:**

The PII-stripped DOM skeleton is the only variable input. Its size is controlled by the sanitizer. Apply these limits before including the skeleton in the user message:

- **Trim depth**: Walk at most 6 levels deep from the feed container. LinkedIn post cards never nest deeper than 5 levels for their structural markers; beyond that is implementation detail.
- **Truncate siblings**: Keep at most 3 sibling post-card elements in the skeleton. The model only needs to see the repeating structural pattern once — it does not benefit from 20 copies.
- **Cap total skeleton length**: 4,000 characters maximum. If the stripped skeleton exceeds this after depth/sibling trimming, truncate from the bottom and append `<!-- skeleton truncated -->`.
- **Total input budget**: System prompt (~600 tokens) + target line (~10 tokens) + skeleton (~800 tokens at 4k chars) = ~1,410 tokens total. Well within Haiku 4.5's 200k context window. No chunking or summarization needed.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Patterns specific to a TypeScript Chrome MV3 service worker calling the Anthropic Messages API for single-shot CSS selector extraction.

### 4b.1 Structured Outputs — TypeScript Type Guard Pattern

There is no Pydantic in this TypeScript project. The equivalent is a hand-written type guard that validates the parsed JSON before the result is used. Do not add a runtime validation library (zod, valibot) for a single use case — the guard below is sufficient.

```typescript
// src/background/index.ts — inline after JSON.parse()

interface SelectorCandidate {
  selector: string;
  rationale: string;
}

interface RederiveModelOutput {
  candidates: SelectorCandidate[];
}

function isRederiveModelOutput(value: unknown): value is RederiveModelOutput {
  if (typeof value !== 'object' || value === null) return false;
  const obj = value as Record<string, unknown>;
  if (!Array.isArray(obj['candidates'])) return false;
  return obj['candidates'].every(
    (c: unknown) =>
      typeof c === 'object' &&
      c !== null &&
      typeof (c as Record<string, unknown>)['selector'] === 'string' &&
      (c as Record<string, unknown>)['selector'] !== '',
  );
}

// Usage with retry:
async function parseAndValidateResponse(raw: string, attempt: number): Promise<RederiveModelOutput> {
  const jsonStr = raw.replace(/^```(?:json)?\n?/, '').replace(/\n?```$/, '').trim();

  let parsed: unknown;
  try {
    parsed = JSON.parse(jsonStr);
  } catch {
    throw new Error(`LLM response is not valid JSON (attempt ${attempt}): ${jsonStr.slice(0, 120)}`);
  }

  if (!isRederiveModelOutput(parsed)) {
    throw new Error(`LLM response failed schema validation (attempt ${attempt})`);
  }

  return parsed;
}
```

**Retry logic:** Attempt the API call up to **2 times** (initial + 1 retry) when a JSON parse error or schema validation error occurs. Do not retry on HTTP 429 (rate-limited by Anthropic — wait and surface to user) or HTTP 401 (bad API key — surface immediately). On the retry, prepend a brief error hint to the user message: `"Your previous response could not be parsed as JSON. Return only a JSON object with a 'candidates' array."` Log each validation failure with `console.warn('[LLB] rederive validation fail attempt N:', errorMessage)`. After 2 failures, throw — the caller falls back gracefully to a null result and leaves the current (broken) selector in place.

### 4b.2 Async-First Design

The MV3 service worker is fully async by nature: `chrome.runtime.onMessage` requires returning `true` to keep the message channel open for an async response. The `rederiveSelector` function is `async` and must be awaited inside the `.then()` / `.catch()` pattern of the message handler — identical to the existing `scorePost` pattern:

```typescript
// Correct: return true to signal async response, then resolve via .then()/.catch()
if (message?.type === 'REDERIVE_SELECTOR') {
  rederiveSelector(message.target as string, message.domSkeleton as string)
    .then(result => sendResponse({ result }))
    .catch(err => sendResponse({ error: (err as Error).message }));
  return true; // REQUIRED — omitting this closes the channel before the fetch completes
}
```

**The one critical mistake:** Returning `false` (or nothing) from the `onMessage` listener while calling an async function. Chrome closes the message channel immediately, `sendResponse` becomes a no-op, and the content script's `Promise` never resolves — it hangs indefinitely or times out. Always `return true` from any `onMessage` branch that calls an async function.

**Stream vs. await:** Do not stream for this use case. The response is a small JSON object (< 256 tokens). Streaming adds implementation complexity (SSE parsing) and provides no UX benefit because the result is used programmatically, not displayed character-by-character. Always `await` the complete response and parse it in one pass.

### 4b.3 Prompt Engineering Discipline

**System vs. user prompt separation:**

The `REDERIVE_SYSTEM_PROMPT` constant must remain in `system` (not in the `messages` array). Anthropic's API treats the `system` field differently from `messages`: it is never included in the conversation history, it is eligible for `cache_control`, and it establishes the model's behavioral constraints cleanly before any user content arrives. Mixing instruction and data in the `user` message makes it harder to cache and harder to inject a guard that the model cannot override via user-turn prompt injection.

The `user` message contains only variable data:
```
Target: POST_CARD

DOM skeleton:
<div role="main" ...>
  <div data-urn="..." ...>
    ...
  </div>
</div>
```

No instructions go in the user message. No "please" or "output as JSON" — those belong in the system prompt.

**Few-shot examples:**

Include one concrete good example and one concrete bad example inline in the system prompt to anchor the model's output format. These are static and benefit from prompt caching:

```
GOOD RESPONSE EXAMPLE:
{"candidates":[{"selector":"div[data-urn*='activity']","rationale":"data-urn with 'activity' identifies post cards"},{"selector":"div[role='article'][data-id]","rationale":"role=article with data-id is a common post card pattern"}]}

BAD RESPONSE EXAMPLE (never do this):
{"candidates":[{"selector":"body div div","rationale":"too broad"},{"selector":"*","rationale":"matches everything"}]}
```

**Token budget:** `max_tokens: 256` is explicitly set and must never be left unset or increased without a deliberate reason. With 1–3 candidates, each with a short rationale, the response comfortably fits in 150–200 tokens. An unbounded `max_tokens` risks the model emitting prose explanations that inflate cost and complicate parsing.

**`stop_sequences`:** Set to `['\n\n\n']` to prevent the model from appending commentary after the JSON object. Claude sometimes adds a follow-up paragraph beginning with "Note:" or "The above selectors..." — three consecutive newlines reliably terminate before that.

### 4b.4 Context Window Management

This extraction call has a fixed, small input window: system prompt + one user turn with a bounded DOM skeleton. There is no conversation history, no growing context, and no retrieval. Context management reduces to a single rule: **keep the DOM skeleton within its 4,000-character budget**.

The sanitizer (`src/content/selector/sanitizer.ts`) must enforce this before the message leaves the content script, not in the service worker after the message arrives. Steps:

1. **Strip PII first** — remove all text nodes, `href`, `src`, `aria-label`, `title`, `alt` attributes.
2. **Trim depth** — walk at most 6 levels from the nearest feed container element.
3. **Limit siblings** — keep at most 3 repeating peer elements at each level (the structural pattern is visible from 2; 3 provides redundancy).
4. **Measure and truncate** — serialize the cleaned subtree to a string; if > 4,000 chars, truncate at the last complete `>` before the limit and close open tags minimally.

If the skeleton exceeds 4,000 characters after all four steps, this indicates an unusually deep or wide DOM change and the heuristic pass should be given one more attempt before the LLM call is abandoned for this cycle.

### 4b.5 Cost and Latency Budget

**Per-call cost estimate (claude-haiku-4-5-20251001, as of June 2026):**

| Token type | Count | Rate | Cost |
|------------|-------|------|------|
| System prompt (cache write, first call) | ~600 tokens | $1.00/MTok × 1.25 | ~$0.00075 |
| System prompt (cache read, subsequent calls within 5 min) | ~600 tokens | $1.00/MTok × 0.10 | ~$0.00006 |
| User message (DOM skeleton, uncached) | ~800 tokens | $1.00/MTok | ~$0.00080 |
| Output (candidates JSON) | ~150 tokens | $5.00/MTok | ~$0.00075 |
| **Total per call (cache miss)** | | | **~$0.0023** |
| **Total per call (cache hit on system prompt)** | | | **~$0.0016** |

At a per-day hard cap of, say, 5 LLM fallback calls per user per day, maximum daily cost is ~$0.012/user/day — negligible. The call is on-breakage-only; most days it fires 0 times.

**Caching strategy:** The `REDERIVE_SYSTEM_PROMPT` block carries `cache_control: { type: 'ephemeral' }`. If LinkedIn's DOM changes trigger two breakage cycles within 5 minutes (e.g., a partial deploy that flaps), the second call reads the system prompt from Anthropic's cache at 10% of the write cost. Note: Haiku 4.5 requires ≥4,096 tokens to activate caching. The system prompt as written (~600 tokens) is below this threshold, so caching will not activate in practice. Two options: (a) accept the negligible cost without caching (recommended — the call is rare enough), or (b) pad the system prompt with static examples and documentation to reach 4,096 tokens (higher upfront token cost per call, cheaper on repeats). Option (a) is recommended for Phase 23.

**Sub-task model routing:** There is no cheaper sub-task to route. The only AI call in Phase 23 is `rederiveSelector`. The breakage detection, heuristic re-derivation, and validation gate are all local TypeScript — zero LLM cost. The LLM call is already on the cheapest viable model (Haiku 4.5). If Haiku 4.5 is retired, the next migration target is the then-current Haiku-tier model as listed at https://platform.claude.com/docs/en/docs/about-claude/models/overview.

**Latency budget:** Haiku 4.5 is the fastest Claude model. Typical first-token latency is 200–400ms; a 256-token response completes in 1–3 seconds end-to-end. This is acceptable for an on-breakage repair path that fires at most once per 5 minutes. The user does not observe this latency directly; the content script continues displaying previously-detected posts while the heal cycle runs asynchronously.

## 5. Evaluation Strategy

> **Runtime note (read first):** This is a client-side TypeScript Chrome MV3 extension with **no backend and no Python**. The template default eval stack (Arize Phoenix / RAGAS / Langfuse) assumes a Python or server runtime and a network-served tracing collector — **none of that applies here** and none of it is adopted. The real eval harness is **Vitest + jsdom fixture-DOM tests** (already the project's installed test runner — `vitest`, `jsdom`, `@vitest/coverage-v8` in `package.json`) running deterministic, code-based assertions against captured LinkedIn DOM snapshots. Almost every dimension below is a **code-based, deterministic** check — the validation gate *is* the eval. **No LLM judge is used:** judging whether a CSS selector is "good" is fully decidable by running `querySelectorAll` against a fixture and counting/inspecting matches, which is cheaper, faster, and more reliable than an LLM grader. Human review is reserved only for labeling fixtures and for the manual live-key path (ADAPT-09).

In-extension monitoring is a small set of counters in `chrome.storage.local` rendered read-only in the existing dashboard health view. Per-LLM-call token/cost tracing is delivered later by Phase 24 (TRACE-02) into the same local store — explicitly **not** part of Phase 23.

**Key Metrics to Track (local, non-identifying):**
1. **Heal events since install** — total count of successful selector heals (heuristic + LLM combined).
2. **Last heal timestamp + source** — when the most recent heal happened and whether it was `heuristic` or `llm` (no selector string stored).
3. **Active selector source per critical target** — `default` / `adapted` / `llm` (already surfaced by SELECTOR-07), with a "last matched on a feed page" recency indicator.
4. **LLM fallback invocation count today** — the `rederiveCallsToday` counter (also the rate-cap input), so a runaway loop is visible.
5. **(Phase 24) per-call input/output tokens + USD cost** — via TRACE-02; not Phase 23.

**Alert Thresholds** (there is no paging in a client extension — these are dashboard warnings / self-checks):
- **Critical selector has not matched on a feed page recently** → SELECTOR-07 warning banner in the health view (signals undetected breakage or a heal that produced a silently-bad candidate).
- **LLM fallback count reaches the per-day cap** → surface "LLM repair limit reached today" so the user understands why no further repair was attempted (also confirms the D8 cap fired correctly).
- **CI: any Critical-dimension fixture test (D1–D4, D6) fails** → block merge (this is the de-facto pre-production alert; the strongest gate the project has).

**Smart Sampling Strategy:** With no permitted server-side interaction log, sampling is **signal-driven and local/manual**: (a) the maintainer reviews the local heal-event counters when an end user reports filtering stopped working, then reproduces against a captured DOM; (b) any LinkedIn DOM that triggered an LLM fallback (heuristics failed) is the highest-value sample — the maintainer captures that structure as a new fixture and folds it into the reference dataset and heuristic logic; (c) A/B-variant divergence reports are prioritized because they reveal cohort-specific DOM the single-developer test set would otherwise miss (Section 1b failure mode 4). All sampling respects the no-PII / no-attempt-history rule: only structure is ever captured, and only by the maintainer reproducing locally, never auto-uploaded.
