# Phase 25.1: Code Review Report

**Reviewed:** 2026-06-14
**Depth:** standard
**Files Reviewed:** 8
**Status:** issues_found

## Summary

This phase adds opt-in capture and export of below-threshold "unflagged" LinkedIn posts as eval negatives. The privacy gate, FIFO/dedup/truncation helper, settings-merge clobber fix, and JSON-export plumbing are all present and broadly correct, and the test coverage for `persistUnflaggedPost` and `buildJsonExport` is solid.

The implementation has one shipping-blocking defect: the only export path that emits `unflaggedPosts` (Export JSON) is hidden whenever `accounts.length === 0`, so a user who enables capture but has no flagged accounts can never export the negatives this phase exists to produce. Beyond that, there are real correctness/privacy gaps: the data-cleanse flow silently leaves `unflaggedPosts` behind (the highest privacy-surface store is the one the user cannot clear), and the capture opt-in is read once at content-script init with no live update or reload hint, so toggling it in the popup appears to do nothing until a page reload.

CLAUDE.md constraints are respected: no `element.remove()` on tracked post nodes (the one `.remove()` call is on an extension-owned tombstone), selectors are untouched, and the service worker remains stateless (capture writes happen in the content script via storage wrappers).

## Critical Issues

### CR-01: Unflagged-post export is unreachable when there are zero flagged accounts

**File:** `src/dashboard/index.tsx:264-266`
**Issue:** The "Export JSON" button — the only UI path that serializes `unflaggedPosts` (via `buildJsonExport(accounts, posts, unflagged)` at line 131) — is rendered only when `accounts.length > 0`. The entire purpose of this phase is to let a user enable capture and later export the captured negatives. A user who turns on "Capture unflagged posts," browses a clean feed (no posts ever flagged), and accumulates hundreds of `unflaggedPosts` has no way to export them, because `accounts.length` is 0 and both export buttons are gated on flagged-account presence. The export silently does not exist. This defeats the deliverable.
**Fix:** Gate the JSON export button on having *any* exportable data, not only flagged accounts:
```tsx
{(accounts.length > 0 || posts.length > 0 || unflagged.length > 0) && (
  <button style={s.actionBtn} onClick={handleExportJson}>Export JSON</button>
)}
```
Optionally surface the unflagged count next to the button (e.g. `Export JSON (${unflagged.length} unflagged)`) so the user can confirm negatives are present.

## Warnings

### WR-01: Data cleanse never removes captured unflagged posts (privacy + stale data)

**File:** `src/dashboard/index.tsx:144-158`, `src/dashboard/dataManagement.ts:75-92`
**Issue:** `handleClean` writes `{ flaggedAccounts, storedPosts, dismissedAccounts: [] }` but never touches `unflaggedPosts`, and `filterCleansed` has no awareness of the unflagged store. The confirmation copy promises "Delete N account(s), N post(s), and all dismissed entries… This cannot be undone," giving the user the reasonable belief that the cleanse purges their stored content. Yet `unflaggedPosts` — explicitly documented in `types.ts:147` and `types.ts:192` as a *broader privacy surface* (it stores text the user never flagged) — survives every cleanse. The one store holding the most sensitive captured text is the only store with no deletion path. `UnflaggedPost` carries `seenAt`, so it is filterable on the same cutoff as posts.
**Fix:** Extend `filterCleansed` (or add a sibling helper) to filter `unflaggedPosts` by `seenAt >= cutoffMs`, include the kept array in the `chrome.storage.local.set` call, and reset the `unflagged` React state. Also reflect the unflagged count in `deriveCleanseCount`/preview and in the confirm dialog so the promise matches behaviour.

### WR-02: Capture opt-in is read once at init; toggling it has no effect until page reload, with no UI cue

**File:** `src/content/index.ts:218,324` and `src/popup/index.tsx:234-248`
**Issue:** `captureUnflaggedPosts` is captured as a `const` inside `init()` (line 218) and closed over by the `detector.detect(...).then(...)` callback (line 324). The `chrome.storage.onChanged` listener (lines 169-180) rebuilds `currentThreshold`/`thresholdAuthors` on a settings change but does **not** update the capture flag. Consequently, a user who ticks the popup checkbox sees an immediate, persisted settings write, but no post is captured on the already-loaded tab until a full reload — and nothing in the popup indicates a reload is required. For an opt-in feature whose entire value is "I turned it on to start collecting," this silent no-op is a real usability/correctness gap. (Note: the existing `autoHideThreshold` has the same init-capture staleness for the in-flight detect path, so this is a pattern issue, but this phase introduces a new user-visible toggle that exposes it.)
**Fix:** Either (a) read the flag live inside the listener — promote `captureUnflaggedPosts` to a module-scope `let` and update it in the `changes['settings']` branch (mirror the `currentThreshold` pattern), then reference the module variable in the detect callback; or (b) add a "reload LinkedIn tabs to apply" hint near the checkbox in the popup.

### WR-03: `persistUnflaggedPost` eviction does an O(n) min-scan that can evict the wrong entry under clock skew

**File:** `src/shared/postStore.ts:109-118`
**Issue:** New entries are always prepended at index 0 with `seenAt: Date.now()`, so in normal operation the oldest entry is always the last element — exactly the invariant `persistStoredPost` relies on with a simple `updated.pop()` (line 64). Instead this function scans for the minimum `seenAt` and splices it out. That is harmless when clocks are monotonic, but `Date.now()` is wall-clock and can move backwards (NTP correction, manual clock change, DST edge). If a freshly prepended entry happens to carry a `seenAt` *smaller* than some existing entry, the min-scan will evict the **just-added newest** entry (oldestIdx could resolve to 0), silently discarding the post the function was called to store. The two stores also now use two different, inconsistent eviction strategies for no stated reason.
**Fix:** Match `persistStoredPost`: rely on the newest-first prepend invariant and `updated.pop()` to drop the tail. If defensiveness against unordered storage is genuinely wanted, still never evict index 0 (the entry just added) — start the scan at `i = 1` against the tail only, or sort-then-truncate.

### WR-04: `mergeSettings` read-modify-write race can drop a concurrent setting

**File:** `src/popup/index.tsx:98-112`
**Issue:** `mergeSettings` does a non-atomic get→spread→set. `saveThreshold` (slider) and `saveCaptureUnflagged` (checkbox) each call it independently. Rapid interaction (e.g. dragging the slider while the checkbox write is in flight) can interleave so that the later `set` is based on a stale read and clobbers the other key — the very clobber this phase set out to fix, reintroduced under concurrency. Single-user popup interaction makes this low-probability, but it is the same failure class.
**Fix:** Serialize settings writes (await the previous write before issuing the next) or maintain a single in-memory settings object that both handlers patch and persist, rather than re-reading storage on each call.

## Info

### IN-01: Debug logging left enabled and unconditionally prints full post text

**File:** `src/content/index.ts:20,319-322`
**Issue:** `const DEBUG = true;` ships enabled, and line 321 logs the entire `postText` of every scored post to the console on every page. Independent of this phase, but directly adjacent to a feature whose headline concern is the privacy of captured post text; logging all post bodies to the console contradicts that posture.
**Fix:** Default `DEBUG` to `false` for shipped builds (or gate on a build flag), and drop `postText` from the log line.

### IN-02: Inconsistent dedup-comment vs. cross-store URN collision

**File:** `src/shared/postStore.ts:96-97`
**Issue:** `persistUnflaggedPost` dedups only within `unflaggedPosts`. A post that is captured as unflagged and later (after a threshold change or re-score) gets hidden will exist in both `storedPosts`/`flaggedAccounts` and `unflaggedPosts` under the same URN, with no reconciliation. This is acceptable for an eval-negatives store (the snapshot is intentionally point-in-time), but it is undocumented and could surprise a consumer who assumes URN is globally unique across stores.
**Fix:** Add a one-line note to the `UnflaggedPost` doc comment in `types.ts` clarifying that an unflagged snapshot is not removed if the same URN is later hidden.

### IN-03: `engineUsed` recorded from per-call result, not validated against capture intent

**File:** `src/content/index.ts:325`
**Issue:** `engineUsed: result.engineUsed` is correct, but when the LLMDetector falls back to the wrapped heuristic on error, the recorded engine reflects whichever path actually produced the score. This is the desired behaviour for eval provenance; flagging only so a future reader does not "fix" it into a static value.
**Fix:** None required — optionally document that `engineUsed` reflects the effective engine after any LLM→heuristic fallback.
