# Phase 25.1: Capture and export unflagged posts for eval negatives - Context

**Gathered:** 2026-06-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Capture the posts the detector scored but did **not** flag (clear "human-looking" negatives), persist them to `chrome.storage.local`, and include them in the dashboard's "Export JSON" output — so the Phase 26 eval has real `human` negatives alongside the existing flagged/hidden positives.

This is an INSERTED phase (decimal 25.1), prerequisite for a *complete* Phase 26 eval. It spans the content script (capture), storage schema (new store), and the export builder (`buildJsonExport`).

**In scope:** content-script capture of below-threshold posts; a new capped storage key; opt-in gating; including the captured posts in the Export JSON.
**Out of scope:** the eval runner itself (Phase 26); labeling UI (labels are added by the user by hand-editing the exported JSON, per 26-CONTEXT D-07).
</domain>

<decisions>
## Implementation Decisions

### What to capture + volume (discussed)
- **D-01:** Capture posts whose merged score is **below `FLAG_THRESHOLD`** — the posts currently dropped by the early return at `src/content/index.ts:323` (`if (mergedScore < FLAG_THRESHOLD) return;`). These are the clear human-looking negatives. This is the clean **complement** to what's already stored (`flaggedAccounts` / `storedPosts` hold the flagged+hidden positives), so the export ends up covering the full score distribution with no overlap.
- **D-02:** New storage key (e.g. `unflaggedPosts`) — a **newest-first array, FIFO-capped at 200**, oldest evicted on overflow. Mirrors the `storedPosts` cap/pattern exactly.
- **D-03:** **Capture all** below-threshold posts (not sampled); the FIFO cap means the store always holds the 200 most-recent unique negatives. **Dedupe by `urn`** so re-seeing a post on scroll does not double-count or churn the cap.
- **D-04:** Capture regardless of detection engine (heuristic or LLM). Capture is **free** — the detector already ran on these posts during normal browsing (in LLM mode the API call + trace already happened), so persisting the non-flagged ones adds no API cost. Record the engine + score that were computed (informational; the eval re-scores fresh anyway).

### Claude's Discretion (areas not selected for discussion — sensible defaults locked)
- **D-05 (Opt-in / privacy):** Gate capture behind a **separate, explicit opt-in toggle, OFF by default** — distinct from the Phase 7 hide-time post-storage opt-in. Capturing *unflagged* posts stores text the user never flagged (a broader privacy surface), so it must be deliberately enabled (this is an eval-prep / power-user feature). Reuse the existing 1000-char truncation convention. Planner may co-locate the toggle with the existing post-storage setting.
- **D-06 (Labeling integrity):** Captured posts are stored **UNLABELED**. Do NOT auto-write `label: "human"` from the fact that they scored low — that is the classifier grading itself (circular) and would corrupt the eval. Ground-truth labels are supplied by the human later (by editing the exported JSON, per 26-CONTEXT D-07). The eval skips unlabeled posts (26-CONTEXT D-09).
- **D-07 (Export shape):** Add captured posts to the Export JSON as a **new top-level `unflaggedPosts: [...]` array** (sibling of `flaggedAccounts`), each entry carrying at least `{ urn, authorId, authorName, text, score, seenAt }` and room for a user-added `label`. Do NOT fake account nesting. Keep `buildJsonExport`'s existing structure intact (purely additive) so the JSON/CSV exports and their tests are unaffected.
- **D-08 (Cross-phase contract — REQUIRED 26 amendment):** Because negatives live in `unflaggedPosts[]` (not under `flaggedAccounts[].posts[]`), **Phase 26's eval input walker must read BOTH** `flaggedAccounts[].posts[]` AND `unflaggedPosts[]`. This amends 26-CONTEXT D-07/D-08. Capture this when planning Phase 26 (or amend 26-CONTEXT directly).

### Folded Todos
None.
</decisions>

## Existing Code Insights

### Reusable Assets
- `persistStoredPost` (queue.ts) + the `storedPosts` 200-cap FIFO array: direct template for the new `unflaggedPosts` store.
- The hide-time opt-in (Phase 7) + 1000-char truncation: reuse the truncation; add a distinct opt-in for unflagged capture.
- `buildJsonExport` (dataManagement.ts): the single place to make the export additive.

### Established Patterns
- Three score bands in the detect flow: `< FLAG_THRESHOLD` (dropped today → our capture target), `FLAG_THRESHOLD..hideThreshold` (flagged, in popup), `>= hideThreshold` (hidden + stored). 25.1 fills the first band.
- chrome.storage.local only; service worker stateless; all caps enforced at write time (storage-schema cap pattern).
- Capture piggybacks on detection that already ran — no new LLM calls, no new cost.

### Integration Points
- Content script: new persist call before the L323 early return, gated on the opt-in.
- Storage: new `unflaggedPosts` key in StorageSchema.
- Dashboard: load `unflaggedPosts` in the existing single `.get([...])`; include it in `buildJsonExport`.
- Phase 26: eval walker reads `unflaggedPosts[]` in addition to `flaggedAccounts[].posts[]` (D-08).
