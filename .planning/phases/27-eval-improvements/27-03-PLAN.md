<objective>
Add a results viewer / run-comparison CLI (`npm run eval-compare -- <results-A.json> <results-B.json> [--format markdown]`) that reads two `eval/results-*.json` files (each is an `EvalRun` after 27-01) and prints a side-by-side diff of the key metrics — engine, posts scored, best-F1 threshold, precision/recall/F1/accuracy, and cost (D-07) — by delegating the diff to a SHARED, pure `compareRuns()` in `src/shared/eval/runs.ts`.

Purpose: Raw `results-YYYY-MM-DD.json` is hard to read and impossible to diff by eye as prompts/models/engines change. A terminal (and optional markdown) comparison table lets the developer see at a glance whether a change improved or regressed the eval, and produces a snippet pasteable into a PR description. Stays a terminal/report tool — no charting UI (D-07).

Forward-compat seam (DATA-MODEL.md guarantee #2): the comparison logic lives in shared (`summarize`, `compareRuns`, `EvalRunSummary`, `EvalRunComparison`, `MetricDelta`) so the Phase 27 `eval-compare` CLI and the Phase 28 dashboard call the SAME pure function — terminal diffs and UI diffs can never drift. `eval-compare.ts` becomes a thin CLI wrapper: parse two paths, read/parse each into an `EvalRun`, call shared `compareRuns`, render. It keeps NO duplicate inline `compareResults`/`ResultsFile`. `EvalRunStore`/`EVAL_RUNS_KEY`/`MAX_EVAL_RUNS` are explicitly OUT of scope for Phase 27 (storage persistence is dashboard-only, Phase 28).

Output: comparison layer added to `src/shared/eval/runs.ts` + its pure-function tests (`src/shared/eval/runs.test.ts`); new thin `scripts/eval-compare.ts` + `scripts/eval-compare.test.ts`. (The `eval-compare` npm script entry is added by Plan 02, which owns package.json.)
</objective>
