Evals dashboard — mockup options

Three design directions for a future in-extension "Evals" page.
Status: throwaway mockups only. Phase 27 ships the CLI-first eval (npm run eval / eval-label / eval-compare). These sketch what a later phase's dashboard page could look like once the pure eval core lives in src/shared/eval/ and can be reused by both the CLI and the page. Pick a direction (or mix) before that phase is planned.

Option A — Single-page console →

Everything in one scrollable column: run controls, metrics, threshold sweep, error analysis, labeling, compare. Mirrors the existing Feed Health dashboard 1:1.

Best for: lowest build cost, familiarity · Trade-off: long page as features grow

Option B — Tabbed workspace →

One tab per deliverable: Run · Label · Results · Compare. Each view is focused; labeling becomes a dedicated click-to-label queue with a progress bar.

Best for: clean separation, scales well · Trade-off: more navigation, hides cross-view context

Option C — Run history / compare-first →

Master–detail: left sidebar lists every stored run; right pane shows the selected run with a live Δ column against a pinned comparison run. Built around tracking quality over time.

Best for: the diff-over-time use case (D-07) · Trade-off: widest layout, heaviest to build
