Evals dashboard — mockup options

Three design directions for a future in-extension "Evals" page.
Decision: ship Option A (single-page console) as the Phase 28 layout. The data model is built to support Option C's run-history + compare view from day one (see DATA-MODEL.md), so C can be added later as pure UI — no data migration. Phase 27 ships the CLI-first eval (npm run eval / eval-label / eval-compare) and emits a run record that the dashboard reuses directly.

✅ Option A — Single-page console (SELECTED) →

Everything in one scrollable column: run controls, metrics, threshold sweep, error analysis, labeling, compare. Mirrors the existing Feed Health dashboard 1:1. Its "Compare to previous run" card is powered by the same run-history store Option C would use.

Best for: lowest build cost, familiarity · Trade-off: long page as features grow

Option B — Tabbed workspace (reference) →

One tab per deliverable: Run · Label · Results · Compare. Each view is focused; labeling becomes a dedicated click-to-label queue with a progress bar.

Best for: clean separation, scales well · Trade-off: more navigation, hides cross-view context

Option C — Run history / compare-first (data ready, UI deferred) →

Master–detail: left sidebar lists every stored run; right pane shows the selected run with a live Δ column against a pinned comparison run. The data structures behind this (EvalRunStore, EvalRunSummary, compareRuns) are defined in DATA-MODEL.md and land in Phase 27, so this view is a later UI-only addition over Option A.

Best for: the diff-over-time use case (D-07) · Trade-off: widest layout, heaviest to build
