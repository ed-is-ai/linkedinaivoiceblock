<objective>
Extract the pure, host-agnostic eval core into a new `src/shared/eval/` module, then re-point the eval scoring loop from the raw `classifyPost` call to a selectable detector engine (`--engine heuristic|llm`, default `llm`) and add best-F1-threshold error analysis (FP/FN) to both the terminal output and the persisted results JSON.

Purpose: The Phase 26 eval bypassed the detector pipeline the extension actually ships, so its per-post `signalBreakdown` used the LLM's own signal vocabulary instead of the heuristic names stored in `flaggedAccounts.signals` (D-01, D-03). Scoring through `HeuristicDetector` makes metrics and signal breakdowns reflect deployed behavior. Error analysis (D-05) turns the results into something actionable by listing the misclassified posts at the chosen threshold.

Reuse seam: the metric/post-mapping logic is host-agnostic — it operates on in-memory data only. Lifting it into `src/shared/eval/` mirrors the Phase 26 classifier extraction to `src/shared/`, so BOTH the CLI (now) and a deferred in-extension "Evals" dashboard page (Phase 28) consume ONE implementation instead of two divergent copies. The shared module carries NO Node `fs`/`process`, NO `chrome.*`, and NO DOM — only pure functions over plain data, so the dashboard (which has chrome + DOM but no Node fs) can import it unchanged.

Output: new `src/shared/eval/` module (pure core + barrel + its own unit tests), a slimmed CLI-only `scripts/eval.ts` (engine flag, engine-branched scoring, FP/FN section, extended results schema, all I/O and printing), expanded `scripts/eval.test.ts`, and an updated `eval-instructions.md`.
</objective>
